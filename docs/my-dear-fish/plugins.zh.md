# 插件养鱼机制

[English](plugins.md) | 中文

“养鱼”在这里不是比喻性的功能名，而是六个插件围绕 DSH 的同一轮对话循环各管一段：记忆决定她记得什么，心情决定她这一轮什么口气，主动搭话决定她什么时候先开口，朗读和 QQ 决定她怎么出现在对话之外，B 站子代理决定她独处时去做什么。这份文档按“共同底座 → 单个插件 → 跨插件链路 → 默认状态 → 改造点”的顺序说明现状，所有结论以 `fish/plugins/` 下的源码为准。

## 共同底座

六个插件都不是独立应用，而是挂在 DSH 的 agent 生命周期上。DSH 每轮从收件箱认领一条消息，组装系统提示与上下文，调用模型，执行工具，写出 `assistant/message`，最后以 `turn/end` 收尾。插件通过 `agent.followup()` 往活着的 agent 收件箱里放一条消息，就能让这一轮像用户打字一样正常开跑；通过 `systemPrompt.context()` 追加每轮变化的内容，通过 `systemPrompt.section()` 放稳定不变的长提示。所有插件的家目录都在 `$DSH_HOME`（Windows 默认 `%USERPROFILE%\.dsh`）下，各自一个子目录或 JSON 文件，不写进插件包。

### 一轮对话的时间线

| 阶段 | 发生的事 | 参与的插件 |
| --- | --- | --- |
| 消息进入 | 用户输入或插件 `followup` 进入收件箱，`source.kind` 记录来源 | 全部 |
| 组装提示 | 人设与常驻提示进 `section`，记忆与心情的当轮内容进 `context` | 记忆、心情 |
| 模型执行 | 模型带着历史、提示和工具清单生成回复，可能调用工具 | 记忆、B 站、QQ |
| 写出回复 | `assistant/message` 写入会话，正文按块累积 | 全部 |
| 回合结束 | `turn/end` 或 `agent/turn-stopping` 触发观察者 | 心情、朗读、QQ |
| 心情判定 | 用一次短模型调用判断这轮心情涨跌，异步写状态 | 心情 |
| 外部投递 | 把这一轮正文排队朗读，或按段落转发到 QQ | 朗读、QQ |
| 下一轮 | 新的记忆与心情通过 `context` 进入下一轮提示 | 记忆、心情 |

### 消息来源与互相识别

`source.kind` 是插件之间最重要的约定。同一条 `user/message`，来源不同，含义完全不同。

| `source.kind` | 谁产生 | 其他插件怎么对待 |
| --- | --- | --- |
| `user` | 用户本人输入 | 记忆的召回查询；心情按真人对话判断 |
| `speak-up` | 主动搭话插件 | 心情按“自己主动开口”判断，不当成用户说的话 |
| `bili-duty-scan` | B 站定时任务 | 心情按“自己干活”判断，不当成用户说的话 |
| `qq` | QQ 桥转进来的消息 | 心情当前会跳过；朗读和 QQ 转发仍会处理这一轮 |
| `plugin` | 插件自己写入的上下文 | 心情跳过，记忆不当成用户消息 |
| `runtime-context` 等 | DSH 宿主注入 | 所有插件都跳过，不算对话内容 |

### 提示注入的两种方式

| 方式 | 位置与稳定性 | 谁在用 | 目的 |
| --- | --- | --- | --- |
| `systemPrompt.section()` | 系统提示中的稳定段落，放在很靠后的位置 | 记忆的 `memory-hint` 常驻提醒 | 不破坏 DeepSeek 的前缀缓存 |
| `systemPrompt.context()` | 每轮追加到对话末尾的上下文 | 记忆的召回结果、心情的当前状态 | 内容每轮变化，也不动系统提示前缀 |

### 数据与开关的位置

| 插件 | 数据位置 | 出厂默认 |
| --- | --- | --- |
| `dsh-fish-memory` | `fish-memory/<会话 id>.json`、`fish-memory-config.json`、`fish-memory-backup/` | 每个会话单独开关，默认关 |
| `dsh-feiyu-mood` | `feiyu-mood/state.json`、`config.json`、`diag.log` | 挂载并自动判断，但目标会话默认写死 |
| `dsh-speak-up` | `speak-up-config.json` | 总开关开，但试运行开、目标会话为空 |
| `dsh-tts-bridge` | `tts-bridge.json` | 自动朗读开，但收听会话为空 |
| `dsh-qq-bridge` | `qq-bridge-config.json` | 总开关关、试运行开、目标会话为空 |
| `dsh-bili-subagent` | `bili-duty/` 下的配置、报告、日志、凭证 | 自动刷关，手动 `bili_scan` 可用 |

## 记忆：dsh-fish-memory

记忆插件解决的是“她怎么能记住上一次说过的事，又不会被旧事淹没”。它不把整段历史塞回提示，而是先按当前这句话去记忆库里找几条真正相关的，再按重要性和新鲜度排序注入；写入则通过 `remember` 工具完成。召回和写入都是本地计算，不调用模型。

### 挂载与生命周期

- 插件每 3 秒扫描一次活着的 agent，只给“这个会话打开了记忆”的 agent 挂载提示段、上下文段和 `remember` 工具。
- 会话关闭开关或归档后，下一跳立即卸载；重新打开不必等 3 秒。
- 分支会话会继承母会话的记忆，但子代理会话被排除，避免 B 站子代理共享主人的记忆。
- 每个会话一个 JSON 文件；配置是全局一份，包含策略参数和各会话开关。

### 数据文件

| 文件 | 内容 |
| --- | --- |
| `fish-memory/<会话 id>.json` | 这个会话的全部记忆条目、召回轨迹、统计 |
| `fish-memory-config.json` | 全局策略、各会话开关、导入设置 |
| `fish-memory-backup/` | 自动备份，防止写坏后无法恢复 |
| `fish-memory-diag.log` | 召回、写入、模型提炼的诊断日志 |

### 召回：一句话到几条记忆

1. 取最近一条用户消息作为查询；插件上下文和系统注入不算。
2. 先过“问句信息量门槛”：像“在吗”这种没有信息量的话直接不翻记忆。
3. 把查询拆成词，剔除在记忆库里出现太多的常用词，再按通用中文稀有度过滤；剩下的稀有词才是线索。
4. 计算证据分 `C`：每个线索词按“库内稀有度 × 她平时说话的稀有度 × 词价”加权求和，再除以总量加平滑常数。整词扩词按全价，碎片按 0.8，只出现在记忆正文里的按 0.6；六字以上的原句命中直接把 `C` 抬到至少 0.85。
5. 计算鲜活度 `A`：普通事件按 30 天半衰期衰减，重要性越高衰减越慢；长期事实不按时间衰减，用固定值参与排序。
6. 计算排序分 `P`：证据、鲜活度、重要性、情绪四项加权；查询里出现时间词只做 1.3 倍排序加权，不影响谁能进门。
7. 用 `C` 过门槛，按 `P` 排序，再按最高 `C` 决定这一趟最多取几条；最后做相似去重、长期事实名额限制和总字数限制，渲染成带相对时间的【你记得的事】。

```
H = 30 × (1 + 2 × I)
A = A0 × 2^(−days / H)
C = Σ(r_store × r_speech × w) / (Σ + 1)
P = C × (0.55 + 0.25 × A + 0.15 × I + 0.05 × E)
```

门槛只卡证据 `C`，不卡排序分 `P`，所以调门槛不会把“该想起来但最近不活跃”的事误伤掉。默认策略是：证据门槛 0.35、最多 6 条、最多 800 字、每天最多记 8 条、长期事实最多占 2 个位置、没写时间的记忆鲜活度按 0.5 算。

### 写入：remember

- `text` 是唯一必填项，一句话说清一件事；`importance` 0 到 1，达到 1 会被标成长期事实。
- `tags` 只是辅助标签；真正决定召回的是正文里的词。
- 同一件事重复记不会新增条目，而是强化旧条目：活跃度按 `A' = A + 0.2 × (1 − A)` 上升，并刷新锚点。
- 新条目与旧条目词相似度达到 0.85 且长度接近时，旧条目自动标成“已被取代”；`取代` 参数用于模型自己知道在更新哪条的情况，按相似度 0.5 找旧条。
- `事实键` 表示“这条讲的是哪件事”，同一个键只保留最新一条，旧条同样标成“已被取代”但保留可恢复。键里不能写具体的值，也不能拿它装每天都会变的流水。

### 模型用在哪儿

日常召回和 `remember` 都不调用模型。模型只用于旧档案导入、词表扩词和少量清洗，且由用户主动触发；不点就不会产生 token。这也意味着记忆的“聪明程度”主要来自词表、稀有度和打分公式，而不是每轮一次模型判断。

### 已知边界

- 记忆默认按会话关闭，新装后需要在设置页为要养的会话打开。
- 召回只拿最近一条用户消息当查询，长对话里的早期话题不会自动带进来。
- 单次注入最多 6 条、800 字；第一条超长时仍会放行，可能挤掉后面所有条目。
- 事实键和“取代”都靠模型填对；填错会把不相关的旧记忆收起来，需要到设置页恢复。

## 心情：dsh-feiyu-mood

心情插件给“大肥鱼”一个跨会话共享的全局状态：一个 0 到 100 的总心情，加七个 0 到 100 的情绪维度。它每轮结束用一次短模型调用判断涨跌，再通过上下文注入影响下一轮语气。心情不是关键词匹配，也不是每次都重写人设，而是一个会衰减、会累积、会回稳的状态量。

### 状态模型

| 字段 | 含义 | 范围与默认 |
| --- | --- | --- |
| `mood` | 总心情基调 | 0 到 100，基线 70，可以降到 0 |
| `dims.happy` | 开心 | 0 到 100，默认 0 |
| `dims.calm` | 平静 | 0 到 100，默认 0 |
| `dims.sweet` | 心里甜 | 0 到 100，默认 0 |
| `dims.heartache` | 心疼 | 0 到 100，默认 0 |
| `dims.worry` | 担心 | 0 到 100，默认 0 |
| `dims.sad` | 难过 | 0 到 100，默认 0 |
| `dims.jealous` | 吃醋 | 0 到 100，默认 0 |

状态全局一份，存在 `feiyu-mood/state.json`，所有会话共享同一个人格状态；时间线只保留最近若干条，用来在设置页回看“为什么变成这样”。

### 每轮怎么判

1. 目标会话的 agent 在 `agent/turn-stopping` 时触发判定，异步执行，不阻塞回复。
2. 从会话事件里从后往前找最后一条真正的触发消息，跳过宿主注入和别的插件消息。
3. 按来源分三种口径：`bili-duty-scan` 是“自己干活”，`speak-up` 是“自己主动开口”，其余真人消息是正常对话。
4. 把这一轮用户内容、助手回复和口径说明交给 `ctx.llm.stream`，要求只输出 JSON：`moodDelta`、七个维度的 `dims`、`reason`。
5. 判定值夹在 −10 到 10；总心情每轮只吃判定值的三分之一，七个情绪维度即时增减。
6. 总心情和维度都没有变化时，不写时间线；有变化时才落盘并记录理由。

模型调用默认跟随当前会话的 provider 和 model，也可以在设置里单独指定判断用的模型；`maxTokens` 为 400，`temperature` 为 0.2，目的是让输出稳定成 JSON。自动判断和目标会话都可以在设置里关掉。

### 衰减与注入

- 总心情向基线回落，半衰期约 3 小时；七个情绪维度向 0 衰减，半衰期约 90 分钟；不足 1 分钟不计算衰减。
- 只有 `injectMood` 开着，且总心情偏离基线至少 5 分、或还有情绪或理由时，才注入一行“此刻你心情如何”。
- 注入用 `systemPrompt.context`，每轮追加在对话末尾，不修改系统提示前缀；最多取两个分值不低于 15 的情绪词。
- 注入句明确要求“用这个心情定这一轮的口气，别把这句话照念出来”，避免模型把状态播报出来。

```
mood(t) = B + (mood(0) − B) × 2^(−min / 180)
dims(t) = dims(0) × 2^(−min / 90)
```

### 界面与设置

- 设置页有总心情、七维情绪、时间线和手动重置；数据全部在本地。
- 网页挂饰通过 `webserver/index-inject` 注入，按心情分五档表情，阈值是 80、62、42、25。
- 路由前缀是 `/dsh-feiyu-mood/`，提供状态、配置、模型列表、重置、会话列表、挂饰脚本和表情图片。

### 已知边界

- 目标会话默认写死成一个示例 id；新装环境里这个会话不存在，必须先在设置页选对目标会话，否则心情不会更新。
- 每轮判定都要一次模型调用；即使判定结果为零也会先花掉这次调用。
- 只认 `user`、`speak-up`、`bili-duty-scan` 三类来源；QQ 转进来的 `qq` 消息会被跳过，可能退回更早的真人消息或直接不判。
- 心情是全局一份，多个会话同时聊天时会互相覆盖同一个人格状态；这是设计选择，不是隔离缺陷。

## 主动搭话：dsh-speak-up

主动搭话插件让“没人说话时她也会先开口”。它不自己拼上下文，而是到点掷一次纯本地骰子，掷中了才往目标会话的收件箱放一条 `source.kind = speak-up` 的消息，让 DSH 正常开一轮。掷骰不花 token，只有真的开口才会调用模型。

### 触发链

1. 定时器按“间隔分钟”到点，默认每 30 分钟一次。
2. 先查总开关、安静时段、目标会话和搭话冷却；任一不满足就跳过。
3. 从“活着、空闲、未归档”的目标会话里随机挑一个；不会自动唤醒冷会话。
4. 按当前是峰时还是谷时取基础命中线，再乘“距她上次说话多久”的时机因子，加上连续没中的加成。
5. 掷一个 0 到 100 的随机数，小于命中线才开口。
6. 开口时构造一条 `user` 角色的消息，来源标成 `speak-up`，交给 `agent.followup()`，再刷新会话落盘。

### 命中线

```
hit = min(100, base × factor + min(cap, misses × bonus))
```

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| 间隔分钟 | 30 | 多久掷一次骰子 |
| 峰时命中线 | 20 | 工作日 9:00–12:00、14:00–18:00 的基础命中线 |
| 谷时命中线 | 60 | 其余时间（含整个周末）的基础命中线 |
| 没中加成 | 10 | 每连续没中一次，下次命中线加 10 点 |
| 加成上限 | 40 | 连续没中的加成最多加到 40 点 |
| 近阈值分钟 / 近因子 | 20 / 0.15 | 距她上次说话不足 20 分钟，命中线乘 0.15 |
| 远阈值分钟 / 远因子 | 360 / 1.5 | 距她上次说话超过 6 小时，命中线乘 1.5 |
| 安静起 / 安静止 | 1 / 8 | 凌晨 1 点到 8 点不开口 |
| 搭话冷却分钟 | 20 | 自己上次开口后至少隔 20 分钟 |

连续没中的次数只存在内存里，重启归零；试运行掷中也归零；设置页的手动按钮不掷骰，也不动计数器。默认总开关开着、试运行也开着，所以新装环境里即使命中也只记日志，不会真的发消息。

### 试运行与手动按钮

- 试运行把“本来要发什么”写进日志，不碰目标会话，适合先观察节奏。
- 手动按钮立即触发一次，不掷骰、不改连续没中次数，用来确认目标会话和文案通了。
- 触发文案可以在设置页改；默认是“好久没人跟我说话了，我该主动去打个招呼”。

### 已知边界

- DSH 只允许 `user` 角色的收件箱消息；插件明确拒绝 `developer` 角色，避免写坏会话日志。
- 不会唤醒冷会话，目标会话必须活着；新装后需要先和目标会话说句话。
- 只有掷中之后才会调用模型，所以“没开口”的那几轮没有模型成本。
- 连续没中计数不持久化，重启后节奏会从头开始。

## 朗读：dsh-tts-bridge

朗读插件分两半：DSH 宿主插件负责“哪一轮说完了、把文字放进队列”，Chromium 扩展负责“把文字送进 DeepSeek 网页并点朗读”。它不自己合成语音，也不依赖系统 TTS，而是借用 `chat.deepseek.com` 页面自带的朗读能力。

### 宿主侧：收集与排队

- 每 1500 毫秒扫描一次配置里要收听的会话，按事件序号增量读取新事件。
- 只聚合 `assistant/message` 里的文本块；工具调用、思考过程不算。
- 一轮只有在 `turn/end` 且结束原因是 `completed` 时，才把整轮文字放进队列；中断的轮不念。
- 队列最多 6 条，满了挤掉最旧的；自动朗读默认开，关掉后只保留手动朗读和队列接口。
- 扩展用 `/next` 领取任务，30 秒内可以重领；150 秒没有回执就丢弃。`/playing` 心跳超过 120 秒视为停止，`/stop` 清空队列。

### 扩展侧：把文字念出来

1. 后台脚本每 1200 毫秒向宿主取任务，并定时确认 DeepSeek 页面还在。
2. 桌面版端口是随机的，扩展先敲固定端口 19387、39871、39872 上的“问路”服务，拿到当前真实地址。
3. 没有 DeepSeek 页面但队列里有话时，后台在非活动标签里打开 `chat.deepseek.com`。
4. 内容脚本把文字加上固定前缀“请只原样重复下面这一段……”填入对话框并发送。
5. 等新的末尾回复和“朗读”按钮出现，点击朗读，再用 `chrome.tabs.audible` 确认页面真的在出声；没声会重试一次。

### 前提与限制

- 必须安装这个 Chromium 扩展，并登录 `chat.deepseek.com`；页面可以放在后台标签，但不能关掉。
- 第一次使用需要真人手动点过一次 DeepSeek 的朗读按钮，浏览器才允许后续自动播放。
- DeepSeek 网页有每日朗读限额，超出后扩展拿不到声音，队列会按失败处理。
- 只念文本，不念工具调用、代码块之外的附件、图片或语音消息。
- 朗读和 QQ 转发互不知道对方存在；同一轮完成时可能既排队朗读，又转发到 QQ。

## QQ：dsh-qq-bridge

QQ 桥把 DSH 会话接到 QQ，分两个方向：DSH 这边说完一轮，把正文按段落发到 QQ；QQ 那边主人发来消息，轮询到之后送进目标会话，让 DSH 正常开一轮。它不依赖机器人账号，而是通过本机的 OneBot 11 HTTP 后端（NapCat 或 SnowLuma）收发。

### DSH 到 QQ

1. 插件盯着目标会话的 `session/event`，记录每一轮最后一条助手正文。
2. 只在 `turn/end` 且结束原因是 `completed` 时发送；中断的轮清空，不发残缺内容。
3. 按轮去重，同一轮不会重复转发。
4. 正文按空行拆成自然段，每段一条消息，段间隔 450 毫秒，像真人连着发。
5. 按配置调用 OneBot 的 `send_private_msg` 或 `send_group_msg`；目标会话归档后跳过。

### QQ 到 DSH

1. 每 4000 毫秒轮询一次私聊历史和群历史，私聊取最近 10 条，群取最近 30 条。
2. 只接受 `user_id` 等于配置里私聊 QQ 号的消息；群里也只认这个号，其他人的消息不进 DSH。
3. 按时间和 `message_id` 去重，纯图片或表情没有正文也会记掉，避免反复拉取。
4. 只取文本段，拼成一句话，构造 `source.kind = qq` 的 user 消息。
5. 通过 `agent.followup()` 送进目标会话；目标会话必须活着，归档或不存在就放弃。

### 前提与默认值

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| 总开关 | 关 | 必须手动打开 |
| 试运行 | 开 | 只记日志，不真的发到 QQ |
| 目标会话 | 空 | 必须选一个要桥接的会话 |
| 私聊 QQ | 空 | 主人的 QQ 号，也是 QQ 到 DSH 的唯一白名单 |
| 转私聊 | 开 | 有私聊号时才生效 |
| 转群 | 关 | 开启后要填群号 |
| NapCat 地址 | `http://127.0.0.1:3000` | OneBot 11 HTTP 后端 |

### 已知边界

- 只处理文本；图片、语音、文件、引用回复都不会转成 DSH 内容。
- QQ 到 DSH 是轮询而不是推送，最坏情况有约 4 秒延迟，也可能在两次轮询之间漏掉已撤回的消息。
- 群聊只认配置里那一个 QQ 号，其他人说话不会进会话。
- 心情插件当前不识别 `qq` 来源，QQ 轮可能不更新心情；这一点见“跨插件耦合与缺口”。

## B站：dsh-bili-subagent

B 站插件让“大肥鱼”在谷时自己去刷视频、读字幕、翻评论，再把值得的内容带回主会话。它不是让主会话直接刷，而是主会话调用 `bili_scan` 派一个子代理去干活；子代理只负责看和汇报，发评论和私信仍由主会话按设置执行。

### 一轮自动刷的流程

1. 定时器每 60 秒检查一次：总开关开、今天自动轮数没到上限、距上一轮至少隔 `gapHours`、当前落在中午或晚上窗口。
2. 条件满足时先记一轮额度，再往目标会话的收件箱放一条 `source.kind = bili-duty-scan` 的消息。
3. 主会话被叫醒后调用 `bili_scan`，插件用 `ctx.subagents.startActivation()` 派一个指定 provider 和 model 的子代理。
4. 子代理按提示词搜近 7 天的视频，标题没意思的跳过，有点意思的读字幕，顺手翻评论区，最多挑 `perScan` 条。
5. 子代理把内部报告交给主会话；报告写入 `out/<日期>.md`，并在回复里提示主会话“这是内部情报，怎么递给主人由你决定”。
6. 主会话按设置决定是否调用 `bili_reply` 发评论并 @，或调用 `bili_send_message` 发私信；两者都关时只把报告聊给主人听。

### 工具与子代理

| 工具 | 作用 | 主要调用者 |
| --- | --- | --- |
| `bili_scan` | 派子代理刷一轮并返回内部报告 | 主会话 |
| `bili_whoami` | 查当前登录的 B 站账号和凭证状态 | 主会话、设置页 |
| `bili_search` | 搜视频，可按综合、播放、最新、弹幕排序 | 子代理 |
| `bili_subtitle` | 取一个视频的字幕全文 | 子代理 |
| `bili_comments` | 取一个视频的热门评论 | 子代理 |
| `bili_reply` | 发评论或回复某条评论 | 主会话 |
| `bili_send_message` | 给指定 UID 发私信 | 主会话 |
| `bili_status` | 看今天跑了几轮、额度、窗口、登录状态、报告路径 | 主会话、设置页 |
| `bili_login_start` | 生成扫码登录二维码 | 设置页 |
| `bili_login_poll` | 查询扫码结果并保存凭证 | 设置页 |
| `bili_setup` | 建独立 venv、安装 Python MCP 依赖 | 设置页 |
| `bili_config` | 读或改插件设置 | 主会话、设置页 |

`bili_search` 有一道硬门槛：配置了最低播放量或最少发布天数时，先在工具层多抓几倍再过滤，子代理根本看不到被过滤的视频。这样“别选低播放量的”不靠提示词自觉，而是直接减少候选。

### 额度、窗口与目标会话

- 额度按“自动刷的轮数”计，不按视频条数；默认每天 5 轮，两轮之间至少隔 3 小时。
- 窗口是北京时间的中午 12:00–14:00 和晚上 18:00–09:00；峰谷总开关默认关，所以新装环境不会自动刷。
- 目标会话留空时，插件自动挑最近聊过、非空、未归档的会话；一个都没有时临时新建一个，用完释放。
- 手动“现在跑一轮”不占自动额度，但仍然走同一个子代理和报告链路。

### 投递闸门

- 评论要同时满足：开了自动评论、填了要 @ 的昵称、投递方式不是“只私信”、每轮评论数大于 0；否则工具直接拒绝，除非调用时明确 `force`。
- 私信要满足：投递方式不是 `off`、填了私信 UID；否则拒绝。
- 两者都开时，这一轮没调用过 `bili_reply` 就不允许发私信；这道闸故意不看 `force`，避免模型总是跳过评论直接私信。
- `bili_reply` 无论成功还是失败都会清掉“欠评论”状态，所以不会把会话锁死。
- 自动评论默认关，必须主人自己打开；这是拿主人的账号公开说话，文档和代码都把默认值设成最保守。

### Python、登录与复核

- 启动时把 `mcp_server.py` 和 `asr.py` 拷到 `bili-duty/` 家目录，再用 stdio JSON-RPC 启动 Python MCP；协议是 `initialize`、`notifications/initialized`、`tools/call` 三步。
- `bili_setup` 在插件家目录建独立 venv，安装 `bilibili-api-python`、`aiohttp`、`mcp`、`qrcode`；没有 uv 时会尝试下载到插件家目录，不污染系统 Python。
- 扫码登录成功后凭证写到 `bili-duty/bili_credential.json`，之后所有搜索、评论、私信都用这份登录态。
- 评论复核从 `seen.md` 取最近最多 6 条，用登录态查顶层评论和楼中楼；7 天内已确认可见的不重复查。查不到时措辞是“没查到”，不写成“没发出去”，因为审核和翻页都可能让刚发的评论暂时不可见。

### 已知边界

- 没有字幕的视频直接跳过；插件不靠标题或摘要猜内容。
- 自动评论和私信会使用主人的 B 站账号，存在风控和社交风险，默认值全部保守。
- 报告是内部情报，主会话不一定完整转述给主人；目前没有强制的“必须汇报”约束。
- 子代理的 provider 和 model 默认写的是 `apii` / `deepseek-v4-pro`，换环境时需要确认这两个名字可用。

## 六者如何串成一天

| 时段 | 发生什么 | 主要插件 |
| --- | --- | --- |
| 凌晨 1–8 点 | 主动搭话安静；若被叫醒仍可正常对话 | 搭话 |
| 上午 | 用户说话，记忆召回、心情判定；可能被主动搭话 | 记忆、心情、搭话 |
| 中午 12–14 点 | 若开启自动刷，B 站子代理可能跑一轮 | B 站 |
| 下午 | 正常对话；朗读和 QQ 按各自开关投递每一轮 | 朗读、QQ |
| 晚上 18 点后 | B 站窗口再次打开；主动搭话进入谷时高命中线 | B 站、搭话 |
| 任意一轮结束 | 心情更新；朗读排队；QQ 转发 | 心情、朗读、QQ |

把这些串起来看，闭环是：用户说话 → 记忆想起相关旧事 → 心情给这一轮定语气 → 模型回复 → 心情按这轮更新 → 朗读/QQ 把回复送出去 → 下一轮记忆可能把新事记下来。主动搭话和 B 站是两条“没有用户输入也能启动”的入口，它们同样走这套循环，只是 `source.kind` 不同，心情对它们的解释也不同。

## 默认状态、成本与风险

| 插件 | 出厂默认 | 模型成本 | 外部依赖 | 主要风险 |
| --- | --- | --- | --- | --- |
| 记忆 | 每会话关 | 召回与写入不花；导入/扩词才花 | 无 | 默认关，容易以为没生效；事实键填错会埋掉旧记忆 |
| 心情 | 开，但目标会话写死 | 每轮一次短调用 | 无 | 目标会话不对就不更新；QQ 轮被跳过 |
| 搭话 | 开，但试运行开 | 命中后才开一轮 | 无 | 默认不发；目标会话为空时不触发 |
| 朗读 | 自动朗读开 | 不调模型，消耗 DeepSeek 网页朗读额度 | Chromium 扩展、DeepSeek 登录 | 页面关闭或限额时没声 |
| QQ | 总开关关、试运行开 | 不额外调模型 | NapCat/SnowLuma、QQ 登录 | 需要本机后端；只处理文本 |
| B 站 | 自动刷关 | 每轮一个子代理，搜索和读字幕都花 token | B 站登录、Python venv | 自动评论/私信有账号风险 |

没有一个插件开箱就全速运转：心情虽然挂载，目标会话却默认写死成一个示例 id；记忆、搭话、QQ、B 站都需要主人选会话或打开开关，朗读需要安装扩展。这是有意的保守默认，不是插件坏了。

## 跨插件耦合与缺口

- QQ 进来的一轮，心情插件会跳过 `qq` 来源，可能回头去判更早的真人消息，或者这一轮干脆不判。结果是 QQ 对话对心情的影响不稳定。
- 朗读和 QQ 互不协调。目标会话同一轮完成时，可能既被排进朗读队列，又被转发到 QQ，造成同一段话出现两次。
- B 站报告是主会话的内部输入，是否转述、转述多少由模型当场决定；没有“必须汇报”的硬约束，也没有“报告必须存档到聊天里”的保证。
- 记忆按会话开关，心情是全局一份。多会话同时使用时，记忆互不共享，心情却共享，二者的人格一致性口径不同。
- 主动搭话只唤醒活着且空闲的目标会话；如果主人长时间不打开那个会话，它不会自己把会话叫起来。

## 改造点地图

| 想改什么 | 改哪里 | 影响 |
| --- | --- | --- |
| 人设、称呼、默认语气 | `fish/bundle/cordis.patch.yml` 的 `personaPrefix` | 影响所有新建 profile，用户 patch 仍可覆盖 |
| 记忆容不容易想起来 | 记忆设置页的策略参数，或 `DEFAULT_POLICY` | 影响召回条数、字数、门槛和每日写入量 |
| 心情的维度、判断频率、判断模型 | 心情设置页与 `lib/index.js` 的维度表和判定链 | 改维度会改变注入文案和表情档位 |
| 主动搭话的频率和时段 | 搭话设置页的命中线、间隔、安静时段 | 先关试运行才会真的发；改命中线比改代码安全 |
| 朗读的触发范围 | 朗读设置页的收听会话、自动朗读开关 | 需要扩展和 DeepSeek 页面配合 |
| QQ 的双向桥接 | QQ 设置页的目标会话、QQ 号、群号、试运行 | 需要本机 OneBot 后端；先开试运行验证 |
| B 站刷什么方向 | B 站设置页的 `keywords`、`scanPrompt`、`perScan` | 影响子代理提示词和每轮挑几条 |
| B 站要不要公开说话 | `autoComment`、`mentionName`、`dmMode`、`dmUid` | 默认全关；开启即用主人账号对外发声 |
| 自动刷的时段和额度 | `peakValley`、`noon`、`night`、`perDay`、`gapHours` | 默认自动刷关，开了才按窗口跑 |
| 插件默认开关本身 | `fish/bundle/cordis.patch.yml` 与各插件默认配置 | 改这里会改变新装环境的出厂行为，需要重新打包 |

改配置能覆盖大部分“养法”，改代码才会动机制本身。按影响从大到小，建议先定人设和默认开关，再定记忆与心情的口径，最后才碰 B 站和 QQ 这类会对外发声的链路。

## 观察与排障

| 现象 | 先看哪里 |
| --- | --- |
| 记忆好像没生效 | 会话设置里记忆是否打开；`fish-memory-diag.log` 的召回与写入记录 |
| 心情一直不变 | 心情设置里的目标会话是否是当前会话；`feiyu-mood/diag.log` 是否有判断失败 |
| 从来不主动搭话 | 总开关、试运行、目标会话、安静时段；`speak-up` 设置页的最近日志 |
| 有文字但没声音 | 扩展是否安装、DeepSeek 页面是否登录并打开、朗读限额；宿主队列状态 |
| QQ 收不到或发不出 | NapCat 是否在 3000 端口、QQ 是否登录、目标会话是否归档、试运行是否还开着 |
| B 站没自动刷 | `peakValley` 是否开、今天额度是否用完、目标会话是否活着；`bili-duty/duty.log` |
| 评论显示成功但别人看不到 | B 站设置页的评论复核结果；`seen.md` 与 `verify-state.json` |

所有插件都把自己的诊断写进家目录，不依赖 DSH 主日志。排障时先看插件自己的日志和设置页，再怀疑模型。

## 结论：先定什么

这份机制说明对应三个需要先拍板的问题。第一，要养的是“记得住、有情绪、会主动找你”的陪伴感，还是“随叫随到、不打扰”的工具感；前者要打开记忆、心情和搭话，后者要保留默认的保守开关。第二，能接受多少模型成本；心情每轮一次短调用，B 站每轮一个子代理，这两项是主要开销。第三，愿不愿意让插件用主人的账号对外说话；B 站自动评论和 QQ 转发都属于这一类，默认值已经全部设成关闭或试运行。

机制本身没有必须改的地方；真正要决定的是哪些开关在出厂时就打开、哪些留给你自己开。确认这三点后，再动 `fish/plugins/` 的代码或 `fish/bundle/cordis.patch.yml` 的默认值，才不会把“养鱼”改成“鱼缸失控”。
